# The gaps, and the field each one maps to

Part of [Context Orchestration Protocols](./index.md).

| # | Gap | Where it showed up | Extension field | Scenario that needs it |
|---|---|---|---|---|
| 1 | Neither protocol reports that a worker **took responsibility** for the work, as distinct from an endpoint having received a message. A2A's `submitted` says the endpoint has it; ACP's `session/prompt` answers only when the turn is over, so the earliest evidence is the first session update. | Conformance: three skips, one A2A and two ACP, each declaring "no `accepted` acknowledgement". | `acknowledgement: {kind, attemptId, at}` | Rejection before acceptance; lost acknowledgement |
| 2 | Neither protocol has a **worker-side checkpoint**. An orchestrator can persist what it holds; it cannot ask a worker to persist what the worker holds, which is why recovery on both bindings today is a retry and not a resume. | Conformance: `checkpoint` refused by both adapters. | `checkpoint: {attemptId, token, at}` | Crash and checkpoint recovery |
| 3 | The **context manifest travels as prose**. Both bindings hand a worker one message, and the structured halves of both — an A2A `DataPart`, an ACP embedded context block — are extension territory that a plain worker does not read. So the notebook reference reached both workers as a line of text, and nothing on the wire said read-only, snapshot, or private. | Example: the objective, its acceptance criteria and its references are rendered once by `objective_prompt` precisely so the two workers are asked the same thing. | `contextManifest: [{uri, access, materialization, sharing, required}]` | Context permission denial |
| 4 | A worker cannot be told its **budget or deadline**, so budget exhaustion is only ever detected by the orchestrator after the spend, never declined by the worker before it. | Example: the execution's policy reaches no worker on either binding. | `policy: {budget, deadline, dataClassification}` | Budget exhaustion |
| 5 | A worker cannot tell a **retry from a duplicate delivery**. The attempt is the orchestrator's concept and never reaches the worker; A2A's task id and ACP's session id identify the work, not the attempt at it. Nor is there a lease: A2A re-attach is polling `tasks/get`, and ACP's is replaying a loaded session. | Conformance: the disconnect and duplicate-delivery scenarios pass only because the *store* tells them apart; both adapters declare re-attach is a fresh look rather than a lease. | `attempt: {attemptId, number, leaseExpiresAt}` | Disconnect after acceptance; duplicate delivery; retry on another worker |
| 6 | An artifact arrives with **no provenance of its own**. A2A artifacts have a name and parts; ACP has no artifact at all, and the adapter registers the turn's text as one. Both hashes, both source references and both trace ids in the example were computed on the client side, so what the orchestrator knows about an output is what it inferred, not what the worker claimed. | Example: `answer_artifact` computes the hash, the attempt attribution and the source references. | `artifactProvenance: {sourceReferences, contentHash, producedAt}` | Conflicting artifact commit |
| 7 | **Steering** a running task is missing from A2A only: ACP prompts the same session again, A2A has no way to add instructions to a task already running — a plain A2A worker gets a new task or nothing. | Conformance and example: `steer` refused by the A2A adapter, supported by the ACP one. This is the one asymmetry the example prints. | `steer: {executionId, attemptId, instructions}` | Lost acknowledgement (steering is the command whose acknowledgement is at stake) |
| 8 | A **structured approval request** exists in ACP only: `session/request_permission` exists and the adapter answers it, while A2A's `input-required` state says a task is waiting without saying what for or offering options. | Conformance: the approval path is exercised on ACP and has nothing to exercise on A2A. | `approvalRequest: {toolCall, options, expiresAt}` | Approval timeout |
| 9 | **Parent, root and child** relationships are not expressible. A2A groups tasks by `contextId` and can reference other tasks, which says they are related and not which is whose parent or how deep; ACP's `session/fork` implies parentage but is unstable and optional, and the reference worker in the example does not declare it. | Predicted, not observed: both the suite and the example are single level today. Recorded as unobserved. | `executionRef: {executionId, parentExecutionId, rootExecutionId, depth}` | Nested delegation; mixed A2A and ACP children |
